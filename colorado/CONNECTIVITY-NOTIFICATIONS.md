# Connectivity notifications

Admin DMs only; no new dashboard controls. Recipients must have Notifications enabled and remain in the bot contact table. Uses the existing acknowledged multipart DM queue and its retry/expiry policy, so delivery is best effort rather than guaranteed.

- First internet check is due five minutes after monitor initialization. Subsequent rounds are five minutes after completion, including during internet outages. No external probes while Wi-Fi is disconnected.
- Successful online analyzer responses reset the five-minute timer and count as connectivity success. Cached/local path names do not. The worker publishes success through a synchronized sequence counter.
- Each probe round tries Microsoft connecttest, then Mozilla success.txt only if needed. Requires HTTP 200 and the exact tiny expected body; redirects are rejected. Plain HTTP avoids TLS memory use but is a reachability heuristic, not cryptographic proof of access to every service.
- Three consecutive failed rounds establish internet loss. After the first failed round, the next two confirmation rounds are scheduled 30 seconds after completion, so confirmation takes about one minute plus request/queue time from the first failure. Successful rounds/online lookups reset this retry sequence and the five-minute timer. Once an outage is confirmed, checks return to five-minute intervals. Lost-since is the first failed round. Two successful rounds/online lookups confirm ordinary internet restoration. After Wi-Fi reconnects, a fresh immediate check determines the combined restoration report: success restores both Wi-Fi and internet; failure reports Wi-Fi restored while retaining the internet loss timestamp. Allocation failure and deferred probes do not count as failed rounds.
- Probes run in a separate task with 3-second HTTP connect/read timeouts, bounded response storage, and platform DNS handling. Path workers and internet probes cannot overlap. New path requests wait for an active probe rather than skipping their lookup. Results spanning a Wi-Fi transition are discarded.
- Wi-Fi changes must persist 10 seconds; initial association gets 30 seconds. Confirmed Wi-Fi loss also marks internet lost through this interface. After Wi-Fi restoration debounce, schedule an immediate internet check and defer the restoration DM until its result (or a fresh successful online path lookup). Communication reminders are deferred while that check is pending; another disconnect cancels the pending restoration.
- USB power, Wi-Fi and internet have separate loss/reminder/restoration formats and independent hourly reminder timers. Each report is one DM, without page numbers.
- USB power: `USB power lost` + loss timestamp + `Battery 4.03V`; hourly `USB power lost since` + original loss timestamp + current battery; restoration `USB power restored` + `Total time xh ym` + current battery.
- Wi-Fi: `Wi-Fi disconnected` + loss timestamp; hourly `Wi-Fi disconnected since` + original loss timestamp. After the fresh reconnect check succeeds: `Wi-Fi: Restored` + `Internet: Restored` + `Total time xh ym`. If it fails: `Wi-Fi: Restored` + `Internet: Lost since` + original internet loss timestamp.
- Internet-only: `Internet lost since` + original first-failure timestamp; hourly `Internet lost since` + original loss timestamp; restoration `Internet restored` + `Total time xh ym`.
- Wi-Fi loss implicitly loses internet access, but sends only the Wi-Fi alert. Internet-only reminders are suppressed while Wi-Fi is disconnected or its reconnect check is pending. A failed reconnect check starts the independent internet reminder interval.
- Loss timestamps remain the original event/first failed probe, not the later confirmation/report time. Durations use monotonic elapsed time so NTP changes do not alter them. Wi-Fi duration ends at reconnection rather than including the internet-check delay. Eastern timestamps; unavailable clocks are labelled honestly.
- Continuous USB power detection is enabled using the tested V4.3 battery-voltage signature. Once-per-second sampling, 10-second average, 25 mV change sustained for 20 seconds; a 60-second boot calibration assumes USB is connected. Detection uses under 200 bytes of fixed RAM and runs indefinitely, independent of the CSV recorder. The CSV test shares the same ADC sample but its buttons and manual markers do not control alert state. Calibration sets initial connected state silently; confirmed transitions drive `onUSBPowerChanged` and admin alerts. Invalid zero readings and sampling gaps reset pending detection. This is a voltage heuristic rather than a physical USB sensor; booting on battery alone cannot establish the correct initial USB state.
- Events include voltage at event time. The bounded RAM queue holds 16 events; under extreme congestion the newest pending event replaces the last queued slot while preserving the event being delivered. Network history and queued reports reset on reboot.
- Confirmed internet loss disables new online path requests. Local names and valid worker cache entries remain usable; unresolved hops fall back to hashes without waiting for the retry interval. A synchronized flag passes connectivity state to the lookup worker. Confirmed recovery re-enables requests and supersedes the old failure backoff. An already-started HTTP request finishes within its existing timeout.
- Each report fits the 120-byte response body. Other commands and sunrise notifications share the radio sender.

Validation: test_connectivity.py, test_connectivity_notifications.py, test_path_queue.py, test_list_delivery.py, test_sunrise_notification.py. Continuous USB detector tests and replay of all three recorded USB tests pass. Firmware build/flash and live alert-delivery verification remain manual.
